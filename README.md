# Многоагентная доставка с гетерогенными роботами: планирование, приоритеты, мосты

Полный пайплайн моделирования и анализа задачи доставки на графе островов
гетерогенной группой роботов (доставщики + строители), с возможностью
строительства новой инфраструктуры. Репозиторий разделён на стабильное
ядро (`core/`) и серию экспериментов/исследований (`experiments/`),
выросших из вопросов об устройстве и качестве эвристик планирования.

## Установка

```bash
pip install networkx matplotlib
```

Зависимостей больше нет — всё остальное (`math`, `itertools`, `random`,
`dataclasses`, `copy`, `typing`) входит в стандартную библиотеку Python 3.

> **Формальный псевдокод** всех алгоритмов (вход/выход, нумерованные шаги,
> математическая нотация, оценки сложности) — в [`ALGORITHMS.md`](static/ALGORITHMS.md).
> Этот README описывает структуру и идеи, `ALGORITHMS.md` — точную формализацию.

## Часть 1 — `core/`: модель и базовый пайплайн

### Постановка задачи

Граф G=(V,E): вершины — острова, рёбра — переправы трёх типов:
- **E_free** — уже построенные (готовые к использованию);
- **E_blocked** — доступные к строительству (есть стоимость постройки и физическая длина);
- **E_impossible** — строительство невозможно (в модели просто не добавляется как ребро).

Два типа роботов: доставщики (везут груз) и строители (строят мосты).
Каждая пара (доставщик+строитель) жёстко привязана друг к другу (1:1).
Грузы заранее закреплены за конкретной парой (`cargo.assigned_pair`) —
это не оптимизируется автоматически, задаётся как вход.

### Алгоритм 1 — приоритет и граф приоритетов

Базовая эвристика приоритета — через прямое (евклидово) расстояние до
ближайшего доставчика и строителя одновременно (bottleneck):

```
p(c_i) = 1 / max( min_k dist(d_k, v_s^i), min_l dist(b_l, v_s^i) )
```

Граф приоритетов строится квантильным разбиением на k дискретных уровней
(уровень 1 — самый приоритетный/левый, уровень k — наименее приоритетный/правый).
Монотонность убывания приоритета вдоль уровней выполняется по построению.

### Алгоритм 2 — выполнение по очереди приоритета

У каждой пары — своя независимая очередь грузов (заданная заранее через
`assigned_pair`). Порядок выполнения внутри очереди одной пары определяется
приоритетом, который пересчитывается перед каждым следующим выбором по
ТЕКУЩЕЙ (уже изменившейся после доставок) позиции этой пары. После доставки
пара остаётся на месте последней доставки — не возвращается на базу.

### Алгоритм 3 — поиск маршрута и минимального набора мостов (эвристика)

Для заданного L (максимальная длина одного моста) строится приведённый
граф: рёбра E_blocked длиннее L удаляются, остальным присваивается вес
`w_build·γ + w_E` (γ — настраиваемый множитель стоимости строительства,
`IslandGraph.build_cost_multiplier`). Перебираются до 12 кратчайших простых
путей, для каждого раздельно считаются W_d и W_b, и выбирается недоминируемый
по (W_d, W_b) путь с минимальной суммой.

**Ограничение достижимости**: если вершина (весь маршрут) уже достижима
через существующие переправы (E_free), строительство не предлагается
вовсе — реализовано через `IslandGraph.shortest_free_path()`. Также при
построении взвешенного графа исключаются избыточные blocked-рёбра, оба
конца которых уже лежат в одной компоненте связности подграфа E_free.

### Алгоритм 4 — Парето-фронт по параметру L

Для сетки значений L прогоняется полный Алгоритм 2, считаются суммарные
W_d_total(L) и W_b_total(L), выделяется Парето-фронт (недоминируемые точки),
и выбирается компромиссная точка L* одним из трёх методов
(`choose_compromise(front, method=...)`):
- `"euclidean"` — минимизация евклидова расстояния до идеальной точки;
- `"chebyshev"` — минимакс (менее чувствителен к линейности фронта);
- `"weighted_sum"` — явная линейная свёртка с заданным весом.

**Важно про форму фронта (выпуклая/вогнутая).** При минимизации двух
издержек геометрически правильный Парето-фронт должен быть вогнутым к
началу координат (зеркально классической кривой производственных
возможностей — там максимизация, здесь минимизация). Признак: при движении
вдоль фронта |наклон| между соседними точками должен убывать. Если вместо
этого растёт — фронт выпуклый, и метод идеальной точки почти всегда выберет
крайнюю, а не промежуточную точку. Функция `is_concave_front()` в
`algorithm_4.py` проверяет это автоматически. Также используется нормировка
по диапазону `(x-min)/(max-min)`, а не по минимуму — это устраняет искажение,
когда оси изменяются в сильно разных масштабах.

### `main.py` — демонстрационный сценарий

10 островов в виде планарного "зигзага" (геометрически без пересекающихся
рёбер — проверено программно), 4 готовых моста, 2 пары, 4 груза. Строит:
граф среды со стоимостями и стартовыми позициями, граф приоритетов,
маршрут каждого груза отдельно, итоговую карту со всеми маршрутами,
Парето-фронт по L.

## Часть 2 — `experiments/`: эвристики и их оценка

### Как Парето-фронт зависит от структуры графа (история исследования)

`experiment_fully_connected.py` исследует вопрос: что будет, если граф
сделать полносвязным по рёбрам E_blocked? Оказывается, при "физически
естественной" (линейной) зависимости стоимости строительства от длины
моста Парето-фронт схлопывается в одну точку — потому что прямое ребро
от старта до финиша почти всегда одновременно и короче ехать, и не дороже
строить, поэтому trade-off между критериями исчезает. Решение —
**квадратичная** (или иная супралинейная) зависимость стоимости
строительства от длины: только она создаёт настоящую конкуренцию между
W_d и W_b при полной связности.

`experiment_more_points.py` отвечает на вопрос "как получить больше точек
на Парето-фронте?" Ответ — не за счёт увеличения числа островов/грузов
самих по себе, а за счёт калибровки **индивидуальных порогов переключения**
между альтернативными маршрутами у разных грузов (точный вывод системы
неравенств приведён в комментариях файла).

`experiment_20_islands_v2.py` — масштабирование тех же идей на 20 островов,
8 пар, 8 грузов, полносвязный граф.

### `heuristic_cheapest_bridge.py` — альтернативная эвристика выбора маршрута

Вместо минимизации суммы (W_d+W_b) среди альтернативных путей (как в
`core/algorithms_1_3.py`), эта эвристика жадно минимизирует **только**
суммарную стоимость строительства, игнорируя стоимость проезда при выборе
маршрута. Результат: при квадратичной калибровке решение зависит от L
только через порог достижимости — после открытия минимально необходимого
моста маршрут больше никогда не меняется, и Парето-фронт по L вырождается
в одну точку. Это иллюстрирует, почему учёт ОБОИХ критериев одновременно
(а не только одного) необходим для содержательной чувствительности
решения к параметру L.

### `scenario_generator.py` — параметризованный генератор сценариев

Произвольное число островов/пар/грузов, полносвязный граф по E_blocked
с квадратичной калибровкой стоимости строительства. Используется во всех
последующих эвристических экспериментах.

### `priority_evaluation.py` — оценка трёх эвристик приоритета

Для каждого груза считается **W_T^i = W_d^i + W_b^i** через жадный
алгоритм построения мостов (от начальной позиции назначенной пары — это
эвристическая, предварительная оценка "как если бы груз был первым").
На основе W_T^i реализованы три эвристики приоритета:

| Функция | Формула | Логика |
|---|---|---|
| `compute_direct_priority` | p = W_T^i | дорогие задачи первыми |
| `compute_inverse_priority` | p = 1/W_T^i | дешёвые задачи первыми |
| `compute_normalized_priority(direction="expensive_first")` | p = W_T^i/ΣW_T^j | то же, что direct, но в виде доли бюджета |

**Математический факт, проверенный в коде** (`verify_direct_equals_normalized`
в `main_priority_comparison.py`): нормировка на сумму — это умножение всех
значений приоритета на одну и ту же положительную константу, что не может
изменить порядок сортировки. Поэтому `direct` и `normalized` дают численно
идентичное расписание; различаются только подписанные на графике приоритетов
абсолютные значения.

Реальное последовательное выполнение (`run_sequential_by_priority`)
пересчитывает стоимость каждой следующей задачи одной и той же пары от её
**фактической** (а не начальной) позиции — расхождение между
эвристической оценкой (estimated) и реальностью (real) и есть мера
качества эвристики приоритета.

### `main_priority_comparison.py` — главный сравнительный скрипт

Запускает все три эвристики на одном демо-сценарии (граф приоритетов всех
трёх рядом) и на двух плотных сериях (30 точек): рост числа грузов
(острова и пары фиксированы) и рост числа островов (пары и грузы
фиксированы), каждая точка усреднена по 5 случайным seed.

**Главный результат**: при росте числа грузов расхождение эвристика/реальность
для `direct`/`normalized` стабилизируется около +2-3% и не уменьшается, а
для `inverse` колеблется ближе к нулю и даже затухает на больших масштабах.
Причина — при выполнении сначала дорогих (обычно дальних) задач пара
смещается на большие расстояния, и эвристическая оценка "от начальной
позиции" расходится с реальностью сильнее, чем при выполнении сначала
дешёвых (обычно близких) задач. При росте числа островов такого
систематического различия между эвристиками не наблюдается — расхождение
определяется случайной геометрией конкретной выборки, а не выбором формулы
приоритета.

### Алгоритм 0 — назначение "груз → пара" (`lpt_assignment.py`, `main_assignment_comparison.py`)

Формальная постановка задачи минимизации общей стоимости расписания (полный
вывод — в `ALGORITHMS.md`, раздел "Постановка задачи"):

```
Φ(π, σ) = Σ_k Σ_j W_T(U_k, σ_k(j) | v^(j-1)_k)  ->  min
```

где π — назначение грузов парам, σ_k — порядок обслуживания внутри пары
(даёт граф приоритетов, Алгоритм 1+2). Сравниваются два варианта для π:

- **LPT** (Longest Processing Time first) — классическая эвристика теории
  расписаний, доказанно минимизирующая **максимум** загрузки (makespan);
- **Greedy Nearest Assignment** — каждый груз назначается паре с минимальной
  стоимостью обслуживания прямо сейчас, явно целится в минимизацию **суммы**.

**Результат**: Greedy Nearest систематически превосходит round-robin baseline
на всех проверенных масштабах (+2.8…+9.4%), тогда как LPT даёт нестабильный
результат (от +4% до −1.9%) — потому что LPT оптимизирован для другой
целевой функции (максимум, а не сумма). В классическом parallel scheduling,
если время обработки не зависит от позиции исполнителя, сумма вообще
инвариантна к назначению — у нас зависимость от позиции есть, но она не
связана с тем, что балансирует LPT.

**Наглядная демонстрация trade-off** (`main_load_balance_demo.py`): три
визуализации показывают это явно —

1. *Столбчатая диаграмма* загрузки каждой пары на одном сценарии: у LPT все
   столбики почти на одном уровне (разброс std≈2-6), у Greedy Nearest один
   столбик может быть в 2-3 раза выше других (std≈16-35);
2. *Точечный график* (Φ, Cmax) на 30 случайных сценариях: облака точек для
   LPT и Greedy Nearest смещены по диагонали в противоположные стороны —
   LPT тяготеет к низкому Cmax, Greedy Nearest — к низкому Φ;
3. *Серия по масштабу*: разрыв между методами по std и по Cmax **растёт**
   с числом грузов — на больших задачах разница в балансировке между
   методами становится только более выраженной.

### Парето-фронт между Φ и Cmax (`main_pareto_assignment.py`)

LPT и Greedy Nearest — это два «полюса» одной обобщённой эвристики
назначения с параметром $\lambda \in [0,1]$ (Алгоритм 0.3 в `ALGORITHMS.md`):

```
U*(λ) = argmin_{U_k} [ λ·ŵ_T(U_k, c_i) + (1-λ)·load̂(U_k) ]
```

При $\lambda=1$ — это Greedy Nearest (минимизация стоимости назначения),
при $\lambda=0$ — жадная балансировка (минимизация текущей загрузки).
Перебор $\lambda$ по сетке даёт множество точек $(\Phi(\lambda), C_{\max}(\lambda))$,
из которых выделяется Парето-фронт.

**Неожиданный результат**: на усреднённых данных оба «полюса»
($\lambda=0$ и $\lambda=1$) оказываются **доминируемыми** — существуют
промежуточные значения $\lambda \approx 0.5$–$0.7$, дающие одновременно
**и** меньшую сумму, **и** меньший максимум, чем оба чистых метода. То есть
ни LPT, ни Greedy Nearest по отдельности не оптимальны по Парето —
выигрывает компромиссная эвристика. Зависимость $\Phi(\lambda)$ и
$C_{\max}(\lambda)$ при этом ступенчатая, а не гладкая — решение
скачкообразно меняется на пороговых значениях $\lambda$ (комбинаторная
природа задачи назначения).

### Эвристика приоритета по расстоянию (формула 2.4) — `distance_heuristic_evaluation.py`

В отличие от трёх эвристик через W_T^i (которые требуют решения подзадачи
маршрута для оценки приоритета), эта эвристика приоритета вообще не решает
подзадачу маршрута — она использует ТОЛЬКО прямое (евклидово) расстояние
от текущей позиции пары до точки погрузки груза:

```
p(c_i) = 1 / max( dist(доставщик, v_s^i), dist(строитель, v_s^i) )
```

Это формула 2.4 ("комбинированный: минимальное расстояние до доставщику
и строителя одновременно") из исходного списка эвристик приоритета. Здесь
сравнивается не стоимость W_T^i, а само РАССТОЯНИЕ: прямая линия "по
воздуху" (эвристическая оценка) против длины пути по графу до той же точки
(реальное расстояние, которое физически проедет доставщик).

**Результат** (`main_distance_heuristic.py`, 30-точечные серии): расхождение
всегда положительное (реальный путь по графу не может быть короче прямой
линии — неравенство треугольника) и держится в стабильном узком коридоре
1.2–2.5% на обеих сериях (рост числа грузов и рост числа островов), без
нарастающего тренда — при росте числа островов расхождение даже слегка
убывает. Это говорит о высокой надёжности геометрической эвристики: дешёвая
оценка "по воздуху" остаётся хорошим предиктором реального расстояния
независимо от масштаба задачи.

## Известные ограничения

- Пары жёстко 1 доставщик : 1 строитель.
- Назначение "груз → пара" задаётся вручную, не оптимизируется автоматически.
- Доставка только "точка-точка" (без множественных пунктов назначения).
- Критерий успеха — доставка ВСЕХ грузов.
- Алгоритм 3 (`core/algorithms_1_3.py`) — эвристика (перебор top-k путей),
  не гарантирует глобальный оптимум на графах с очень большим числом
  альтернатив; параметр `k_alternatives` нужно увеличивать вручную для
  более богатых графов.
- Маршрут строителя при нескольких мостах в одной задаче строится
  последовательно (от моста к мосту в порядке появления на пути
  доставщика), без рассмотрения альтернативного порядка обхода.
