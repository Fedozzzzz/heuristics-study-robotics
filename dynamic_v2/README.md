# robot_delivery_v2 (dynamic_v2)

Вторая реализация динамической модели многороботной доставки на графе-острове
-- по алгоритму «Алгоритм динамической модели -- итоговая версия по шагам»
(Шаги 0-6), но с **другим способом формирования приоритета грузов и пар**,
чем в [`dynamic/`](../dynamic/README.md).

## Главное отличие от `dynamic/`

| | `dynamic/` | `dynamic_v2/` (этот проект) |
|---|---|---|
| Приоритет груза | Считается для КОНКРЕТНОЙ пары "коалиция x груз" -- зависит от того, где сейчас стоят доставщик и строитель этой коалиции (`ESTIMATE-TASK-COST`, куда входит их подъезд к грузу). | Считается для груза **независимо от роботов** -- только стоимость его собственного маршрута `c_start -> c_finish` (`ROUTE-AND-COST`), без подъезда каких-либо роботов. |
| Порядок формирования | Сначала собираются ВСЕ коалиции (жадное паросочетание доставщик-строитель по расстоянию), затем строится таблица "коалиция x груз" и раунд разбирается по этой таблице. | Сначала грузы ранжируются по приоритету САМИ ПО СЕБЕ (Шаг 1), затем под каждый выбранный по приоритету груз собирается СВОЯ коалиция (Шаг 2): ближайший свободный доставщик + свободный строитель с минимальным числом новых мостов. |
| Эвристик приоритета | 10 вариантов (`cost_direct`, `cost_inverse`, `cost_normalized`, `cost_by_agent_type`, 4 дистанционных, выпуклая комбинация Greedy-Nearest/LPT, random baseline). | 3 варианта: `direct` (p = W_C) и `inverse` (p = 1/W_C) из постановки задачи, плюс перенесённый из `dynamic/` `random` baseline (p ~ U(0,1)). |
| Алгоритмы распределения внутри раунда | `greedy` / `round_robin`. | Только один способ -- отбор N грузов по приоритету с формированием коалиций под них (постановка задачи не описывает альтернатив). |
| Диагностическая вилка оценка/факт | 5 метрик: `real`, `estimated_raw`, `estimated_pool`, `estimated_precollision`, `estimated_prognosis` + 4 gap-метрики. | Только 2 метрики: `real` и `estimated_raw` (+ `gap_raw`) -- намеренно упрощено по запросу, промежуточные оценки (`estimated_pool`/`estimated_precollision`/`estimated_prognosis`) убраны из `diagnostics.py`, CSV и графиков. |

То, что **не** отличается (перенесено без изменений): модель графа-острова
(`graph.py`), `ROUTE-AND-COST`/`ESTIMATE-TASK-COST` (`costs.py`), Шаг 0
(проверка достижимости, `feasibility.py`), Шаг 4 (разрешение коллизий за
общий мост -- случайный победитель, для остальных бесплатно), Шаг 5
(обновление позиций), и то, что `built` (возведённые переправы) --
**глобальное состояние, общее для всех раундов: однажды построенный мост
никогда не строится повторно**.

## Алгоритм по шагам (см. также docstring `robot_delivery_v2/scheduler.py`)

- **Шаг 0** (проверка достижимости) -- `check_feasibility`
  (`robot_delivery_v2/feasibility.py`), без изменений относительно `dynamic/`.
- **Шаг 1** (оценка приоритетов грузов, `robot_delivery_v2/cargo_priority.py`,
  `RANK-CARGOS`) -- для каждого ещё не доставленного груза считается
  `W_C = ROUTE-AND-COST(G, c_start, c_finish, built).travel_cost + build_cost`
  -- стоимость маршрута погрузка -> разгрузка с учётом готовых переправ и
  стоимости построения ещё не готовых, БЕЗ учёта перемещения роботов до точки
  погрузки. Приоритет `p = direct(W_C)` или `p = inverse(W_C) = 1/W_C`.
  Список сортируется по убыванию `p`. Пересчитывается заново в начале КАЖДОГО
  раунда, т.к. `built` меняется между раундами (уже построенные мосты
  удешевляют маршрут).
- **Шаг 2** (формирование коалиций и назначение грузов,
  `robot_delivery_v2/scheduler.py`, `SELECT-ROUND`):
  1. Число коалиций раунда:
     `N = min( floor((|R_d| + |R_b|) / 2), |R_d|, |R_b|, |pending| )`.
     При `|R_d| == |R_b|` (обычный случай -- см. `--n-pairs` в CLI) это
     сводится к `N = |R_d| = |R_b|`, т.е. "число пар роботов"; общий `min()`
     не даёт формуле выйти за физически возможное число биективных пар
     доставщик-строитель, если доставщиков и строителей не поровну.
  2. Грузы разбираются В ПОРЯДКЕ УБЫВАНИЯ ПРИОРИТЕТА, пока не набрано `N`
     коалиций. Для каждого груза:
     - **доставщик** -- ближайший ЕЩЁ СВОБОДНЫЙ доставщик к точке
       погрузки (`dist()` на графе `G`, с учётом переправ, доступных к
       возведению, но без учёта постройки -- как в `form_coalitions`
       из `dynamic/`);
     - **строитель** -- среди ещё свободных строителей выбирается тот, для
       кого `ESTIMATE-TASK-COST(груз, выбранный доставщик, строитель, built)`
       требует построить МИНИМАЛЬНОЕ число НОВЫХ мостов (маршрут доставщика +
       подъезд строителя); при равенстве -- **минимальную суммарную
       стоимость их постройки** (tie-break, выбран как более простой из двух
       вариантов, допущенных постановкой задачи: "можно с учётом длины пути,
       либо просто со стоимостью построения мостов").
     - если для груза не находится ни доставщика, ни подходящего строителя
       (все свободные роботы исчерпаны, либо маршрут для всех комбинаций
       недостижим при текущем `built`) -- груз пропускается **в этом раунде**
       и остаётся `pending` для следующего (со свежепересчитанным приоритетом).
- **Шаг 3** (эвристическая оценка раунда без учёта возводимых переправ) --
  `W_T_initial` каждой сформированной коалиции (полная `ESTIMATE-TASK-COST`
  ДО скидки за внутрираундовое резервирование мостов); хранится в
  `ScheduleRecord.W_T_initial` (используется как `p_rank`/для Шага 4), но
  отдельной диагностической метрикой не выводится -- `diagnostics.py`
  сравнивает факт только с `estimated_raw` (см. ниже).
- **Шаг 4** (конфликт за один и тот же ещё не построенный мост между
  несколькими коалициями раунда) -- случайный победитель строит мост за свой
  счёт (`won_bridges`), для остальных коалиций проезд по нему в рамках этого
  и всех последующих раундов бесплатен (`built` глобален).
  Воспроизводимость обеспечивается параметром `rng_seed`.
- **Шаг 5/6** (`RUN-DYNAMIC-ROUNDS`) -- барьерная синхронизация раунда по
  самой долгой доставке, позиция доставщика после раунда -- точка разгрузки,
  позиция строителя -- конец последнего ЛИЧНО построенного им моста (или
  прежняя позиция, если сам ничего не строил); цикл повторяется, пока
  остаются недоставленные грузы.

## Установка

```bash
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

Нужен Python ≥ 3.9. Единственная внешняя зависимость -- `matplotlib` (для
графиков); граф, Dijkstra и планировщик реализованы на чистом Python.

## Быстрая проверка

```bash
python3 tests/test_core.py
```

Должно вывести `Все тесты пройдены (22)`.

## Список доступных эвристик приоритета груза

```bash
python3 -m robot_delivery_v2.cli --list-heuristics
```

| Ключ | Формула | Смысл |
|---|---|---|
| `direct` | p = W_C | Дороже маршрут груза -- выше приоритет |
| `inverse` | p = 1 / W_C | Дешевле маршрут груза -- выше приоритет |
| `random` | p ~ U(0,1) | Baseline: не зависит от стоимости маршрута -- эквивалент случайного распределения приоритета грузов (перенесено из `dynamic/`, см. `random_priority`) |

## Прогон экспериментов

Можно сравнить любое подмножество эвристик, включая все 3 сразу:

```bash
python3 -m robot_delivery_v2.cli \
    --heuristics direct inverse random \
    --n-islands 20 \
    --n-pairs 3 \
    -n 20 \
    --n-runs 10 \
    --seed 42 \
    --trace \
    --output-dir outputs
```

Устройство развёртки и флаги генератора графа (`--free-prob`,
`--build-cost-factor`) такие же, как в [`dynamic/README.md`](../dynamic/README.md),
за вычетом всего, что касается `--assignment-algos` (в этой модели нет
альтернативных алгоритмов распределения внутри раунда). В `--output-dir`
сохраняются:

- `experiment_results.csv` -- сырые данные по каждому прогону (эвристика,
  seed, `n_islands`/`n_cargos`/`n_pairs`, `real`, `estimated_raw`, `gap_raw`,
  `idle_total`, число раундов, флаги достижимости и полной доставки);
- `real_vs_estimated_bars.png` -- средние `real`/`estimated_raw` по каждой эвристике;
- `gap_raw_vs_ncargos.png` -- как разрыв `estimated_raw` vs `real` (%) растёт с числом грузов, отдельная линия на эвристику;
- `round_trace.png` (только если указан `--trace`) -- накопительный real vs estimated_raw по раундам для одного прогона.

При `--heuristics` с БОЛЕЕ ЧЕМ ОДНОЙ эвристикой (в т.ч. со всеми тремя)
дополнительно строятся:

- `real_vs_ncargos.png` -- средняя фактическая стоимость доставки (`real`) в
  зависимости от `n_cargos`, ОТДЕЛЬНАЯ ЛИНИЯ НА КАЖДУЮ ЭВРИСТИКУ, все на одном графике;
- `win_rate.png` -- доля сценариев, где у эвристики минимальный `real`.

```bash
python3 experiments/compare_direct_vs_inverse.py \
```

### Насколько direct/inverse лучше случайного приоритета?

`experiments/compare_direct_vs_random.py` -- аналог
`dynamic/experiments/compare_direct_vs_random.py`, сравнивающий `direct`
(p = W_C) с `random` (p ~ U(0,1), baseline) на одних и тех же сценариях:

```bash
python3 experiments/compare_direct_vs_random.py \
    --n-islands 18 --n-pairs 3 -n 24 --n-runs 15 --seed 0
```

Сохраняет те же три графика + CSV в `outputs/direct_vs_random/`. Через
`--heuristics inverse random` можно сравнить `random` с `inverse` вместо

### Сравнение с точным оптимумом (competitive ratio)

Все метрики выше (`real`, `estimated_raw`, win-rate) сравнивают эвристики
ДРУГ С ДРУГОМ или с их же собственной эвристической оценкой -- нет
независимого ориентира "а насколько это вообще далеко от оптимума". Для
МАЛЕНЬКИХ сценариев задачу можно решить ТОЧНО полным перебором с ветвями и
границами (`robot_delivery_v2/optimal.py`, `solve_optimal_brute_force`):
минимальная суммарная стоимость (W_d + W_b), достижимая ЛЮБОЙ
последовательностью назначений груз/доставщик/строитель -- без ограничений
Шага 2 модели (без фиксированного N на раунд, без отбора по приоритету p).
Это релаксация модели, поэтому `optimal <= real` для любой эвристики, и

```
competitive_ratio = real / optimal   (>= 1, чем ближе к 1 -- тем лучше)
```

даёт АБСОЛЮТНУЮ оценку качества, а не только относительное сравнение.

```bash
python3 experiments/compare_with_optimum.py \
    --n-islands 8 --n-pairs 2 --n-cargos-min 2 --n-cargos-max 5 --n-runs 15 --seed 0
```

**ВНИМАНИЕ: полный перебор экспоненциален по числу грузов** -- держите
`--n-cargos-max` маленьким (защитный предел `--max-cargos`, по умолчанию 7,
поднимает `ValueError` при попытке превысить его). На дефолтных параметрах
(8 островов, 2 пары, 2..5 грузов, 15 прогонов на точку) полный прогон занимает
~5 секунд.

Сохраняет в `outputs/vs_optimum/`: `vs_optimum_results.csv` (real, optimal,
competitive_ratio, solve_time_s по каждому прогону), `competitive_ratio_bars.png`
(средний competitive ratio по каждой эвристике) и `competitive_ratio_vs_ncargos.png`
(тот же ratio в зависимости от числа грузов, отдельная линия на эвристику).

**Результат на дефолтных параметрах** (8 островов, 2 пары, 2..5 грузов, 15
прогонов/точку, seed=0): все 60 сценариев успешно решены точно, все три
эвристики полностью доставляют грузы. Средний competitive ratio:

| Эвристика | avg | min | max |
|---|---|---|---|
| `direct` | 1.542 | 1.000 | 3.685 |
| `inverse` | **1.453** | 1.000 | 3.509 |
| `random` | 1.497 | 1.000 | 3.509 |

То есть даже на этих крошечных сценариях реальная стоимость доставки в
среднем в **1.45-1.55 раза выше** теоретического оптимума (при полной
свободе назначения без ограничений Шага 2), хотя в отдельных прогонах
эвристика попадает точно в оптимум (`min = 1.000`). Разрыв растёт с числом
грузов (`competitive_ratio_vs_ncargos.png`: ~1.5 при 2 грузах, но уже
~1.5-1.75 при 5) -- ожидаемо, т.к. с ростом `n_cargos` жадный локальный отбор
Шага 2 (без возможности пересмотреть уже принятые решения) накапливает всё
больше субоптимальных развилок. На этом небольшом сэмпле `inverse` был в
среднем чуть ближе к оптимуму, чем `direct` и `random`, но разница мала и
сама по себе не является статистически надёжным выводом при таком объёме
выборки.

## Программное использование

```python
from robot_delivery_v2.scenario import generate_scenario
from robot_delivery_v2.experiment import run_single

scenario = generate_scenario(n_islands=18, n_cargos=12, n_pairs=3, seed=1)
result, bracket = run_single(scenario, "direct")

print(result.feasible, result.all_delivered, result.n_rounds)
print(bracket.real, bracket.estimated_raw, bracket.gap_raw)
```

## Известные допущения / упрощения реализации

- Как и в `dynamic/`, Шаг 0 проверяет достижимость только по связности графа
  (`E_ready ∪ E_blocked`); дистанционные допущения из `dynamic/` здесь не
  нужны, т.к. в `dynamic_v2` нет дистанционных/геометрических эвристик.
- Формула размера раунда `N = min(floor((Rd+Rb)/2), Rd, Rb, |pending|)`
  явно обобщает пример из постановки задачи (`Rd = Rb = 2` -> `N = 2`) на
  случай неравного числа доставщиков и строителей -- `min()` гарантирует,
  что число коалиций никогда не превысит физически возможное число
  биективных пар доставщик-строитель.
- Если для груза-кандидата (в порядке приоритета) не находится ни
  свободного доставщика, ни свободного строителя (например, все подходящие
  роботы уже заняты более приоритетными грузами этого же раунда), груз
  пропускается в этом раунде без остановки алгоритма -- он останется
  `pending` и получит свежепересчитанный приоритет в следующем раунде.
  Это не описано явно в постановке, но необходимо для корректной работы
  цикла: иначе жадный отбор "только первых N по приоритету" мог бы застрять,
  если топ-N грузов физически недостижимы для оставшихся свободных роботов,
  а грузы ниже по списку -- достижимы.
- Tie-break строителя (когда у нескольких строителей одинаковое минимальное
  число новых мостов) реализован через минимальную суммарную стоимость их
  постройки -- второй из двух вариантов, явно допущенных постановкой задачи
  ("можно с учётом длины пути, либо просто со стоимостью построения мостов").
- `estimated_raw ≥ real` -- гарантированное свойство модели (проверено
  тестом `test_estimated_raw_never_below_real`), по той же причине, что и в
  `dynamic/`: `estimated_raw` пересчитывает каждую доставку в одиночку с
  `built = ∅`, тогда как `real` использует накопленный за все раунды `built`
  плюс скидку за внутрираундовые коллизии (Шаг 4) -- дополнительная
  информация не может увеличить стоимость.
- Возведённые переправы -- глобальное состояние, общее для ВСЕХ раундов:
  однажды построенный мост никогда не строится повторно ни той же, ни другой
  коалицией ни в этом, ни в последующих раундах (проверено тестом
  `test_bridges_never_rebuilt_across_rounds`).
- Диагностическая вилка оценка/факт намеренно упрощена относительно
  `dynamic/`: `estimated_pool` (коррекция за переиспользование мостов),
  `estimated_precollision`/`estimated_prognosis` (оценка ДО скидки за
  внутрираундовые коллизии) и соответствующие им `gap_pool`/
  `gap_precollision`/`gap_prognosis` убраны из `diagnostics.py`,
  `ExperimentRow`/CSV и графиков -- остались только `real`, `estimated_raw`
  и `gap_raw`.

```
│   └── compare_with_optimum.py
├── requirements.txt
└── README.md
```
