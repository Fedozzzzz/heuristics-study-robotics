# robot_delivery_static (static_v2)

Реализация **статической модели** многороботной доставки на графе-острове:
пары роботов формируются заранее, грузы распределяются по приоритетам для
каждой пары в самом начале и больше не перераспределяются.

Главное содержательное отличие от динамической модели
([`dynamic_v2/`](../dynamic_v2/README.md)): при оценке приоритета грузов и их
распределении **не учитываются промежуточные перемещения роботов** (после
первой же доставки пара стоит уже не там, где стартовала) и не учитываются
переправы, возведённые к тому моменту кем-либо ещё. Это потенциально даёт
завышенную оценку стоимости выполнения всех операций -- разрыв измеряется
метрикой `gap_static` (см. ниже: на дефолтных параметрах он растёт с числа
грузов от +4% до +70…+120%).

Отличие от старого [`static/`](../static/README.md): та реализация построена
на другом ядре (`networkx`, ограничение длины моста `L`, назначение "груз ->
пара" задаётся вручную). `static_v2` использует то же ядро, что `dynamic_v2`
(собственный граф, `ROUTE-AND-COST` / `ESTIMATE-TASK-COST`, Шаг 0), поэтому
обе модели можно прогонять на буквально одних и тех же сценариях и сравнивать
напрямую.

## Сравнение со `dynamic_v2` по шагам

| | `dynamic_v2/` | `static_v2/` (этот проект) |
|---|---|---|
| Пары роботов | Коалиция собирается заново КАЖДЫЙ раунд под выбранный по приоритету груз. | Пары формируются ОДИН раз (Шаг 2, по минимальному расстоянию доставщик-строитель) и не пересобираются до конца прогона. |
| Приоритет груза | Считается по стоимости собственного маршрута груза `c_start -> c_finish`, независимо от роботов; пересчитывается каждый раунд. | Считается для ЯЧЕЙКИ таблицы "пара x груз" -- по полной стоимости доставки этой парой из её НАЧАЛЬНОЙ позиции; считается ОДИН раз в начале. |
| Распределение грузов | В начале каждого раунда берутся N самых приоритетных грузов из ещё не доставленных. | Все грузы распределяются между парами один раз (Шаг 3), у каждой пары -- свой список на весь прогон. |
| Порядок исполнения | Раунд = N доставок, подбираемых заново. | Раунд r = каждая пара везёт r-й груз своего списка. |
| Оценка/факт | `real` vs `estimated_raw`. | `real` vs `estimated_static` (оценка Шага 3, ради которой модель и строится) vs `estimated_raw` (контрольная). |

Без изменений перенесены: модель графа (`graph.py`), `ROUTE-AND-COST` /
`ESTIMATE-TASK-COST` (`costs.py`), Шаг 0 (`feasibility.py`), правило конфликта
за общий мост (случайный победитель платит, остальным бесплатно), правило
обновления позиций после доставки и то, что `built` -- **глобальное состояние:
однажды построенный мост никогда не строится повторно**.

## Алгоритм по шагам

- **Шаг 0. Проверка достижимости решения** (`feasibility.py`). Строится
  `G' = (V, E_ready ∪ E_blocked)`; все точки погрузки/разгрузки должны лежать в
  одной компоненте связности `G'` (условия 1 и 2 постановки сводятся к этой
  единой проверке, т.к. компонента по готовым переправам всегда вложена в
  компоненту по готовым + доступным к постройке). Дополнительно в этой
  компоненте должен найтись хотя бы один доставщик и хотя бы один строитель.
  Иначе -- выход из алгоритма без единого раунда.

- **Шаг 2. Формирование пар роботов** (`pairing.py`, `FORM-PAIRS`). Все
  комбинации (доставщик, строитель) сортируются по расстоянию в графе
  (Дейкстра по всем переправам, кроме `IMPOSSIBLE`, без учёта стоимости их
  постройки); список проходится один раз, пара берётся, если оба робота ещё
  свободны -- **жадное паросочетание по минимальному расстоянию**. Роботы,
  оставшиеся без пары (неравное число доставщиков и строителей либо
  недостижимость), в работе не участвуют.

- **Шаг 3. Распределение грузов между коалициями** (`assignment.py`,
  `ASSIGN-CARGOS`), два этапа.

  *Этап 1 -- таблица пара x груз.* Для каждой пары и каждого груза считается
  `W_T = ESTIMATE-TASK-COST(...)` **от начальных позиций пары и при
  `built = ∅`**: подъезд доставщика к точке погрузки, доставка до точки
  разгрузки, работа строителя (все мосты маршрута доставщика + мосты, нужные
  самому строителю, чтобы до них добраться). Приоритет ячейки
  `p = heuristic(W_T)`; в эвристике постановки (`direct`) приоритет прямо равен
  стоимости -- "сначала дорогие грузы".

  *Этап 2 -- свёртка в список и один жадный проход.* Реализованы два режима
  (`--assignment`):

  | Режим | Правило |
  |---|---|
  | `literal` | Буквально по постановке: таблица сворачивается в один список записей `(p, груз, пара)`, отсортированный по убыванию `p`, и проходится ОДИН раз -- первая встреченная запись с ещё не назначенным грузом отдаёт груз своей паре. При `direct` груз достаётся паре, для которой он САМЫЙ ДОРОГОЙ; при `inverse` (p = 1/W_T) -- наоборот, самой дешёвой. |
  | `cheapest` | Грузы разбираются в том же порядке убывания приоритета, но каждый груз отдаётся паре с МИНИМАЛЬНОЙ для неё стоимостью (классический greedy-nearest). |
  | `lpt` | Полноценный LPT (Longest Processing Time first, Graham 1969): грузы разбираются по убыванию РАЗМЕРА задачи, каждый достаётся НАИМЕНЕЕ ЗАГРУЖЕННОЙ паре. Подробно -- ниже. |

  Режимы реализованы именно для того, чтобы прямую и обратную эвристику можно
  было сравнивать и с буквальным правилом постановки, и с явным greedy-nearest
  (`experiments/compare_assignment_modes.py`), и с классической эвристикой
  теории расписаний (`experiments/compare_lpt_assignment.py`).

  *Режим `lpt`* (`assignment.assign_lpt`, `ASSIGN-LPT`) -- список-планировщик
  для параллельных машин: "машины" -- пары роботов, "работы" -- грузы, "время
  обработки" -- оценка `W_T` Шага 3. Для `P||C_max` LPT даёт гарантию
  `C_max^LPT / C_max^opt <= 4/3 - 1/(3m)`. Три этапа:

  - *Этап A -- размер задачи.* В классической постановке время обработки от
    машины не зависит, здесь зависит (`W_T(U_k, c_i)` у разных пар разное), то
    есть машины НЕидентичные. Чтобы сортировка вообще имела смысл, строка
    таблицы сворачивается в скаляр `s(c_i)` правилом `--lpt-size`: `min` (по
    умолчанию -- стоимость у лучшего исполнителя, "внутренняя" трудоёмкость
    груза), `mean` или `max`.
  - *Этап B -- порядок.* Грузы сортируются по убыванию `p = heuristic(s(c_i))`.
    Эвристика применяется к размеру задачи, а не к стоимости конкретной пары:
    в LPT порядок обязан быть общим для всех машин. Отсюда `direct` -- в
    точности LPT (длинные работы первыми), `inverse` -- SPT (короткие первыми),
    `random` -- list scheduling без сортировки, baseline Грэма.
  - *Этап C -- выбор пары*, правило `--lpt-rule`:

    | Правило | `U* = ...` | Смысл |
    |---|---|---|
    | `load` | `argmin load[U_k]` | Классический Грэм: пара с наименьшей накопленной загрузкой; стоимость груза именно для неё в выборе не участвует (при равных загрузках -- та, которой груз дешевле). |
    | `completion` | `argmin (load[U_k] + W_T(U_k, c_i))` | Поправка на неидентичность машин (`R||C_max`): минимизируется момент ЗАВЕРШЕНИЯ, а не начала. Пара, для которой груз втрое дороже, его не получит, даже будучи сейчас самой свободной. |

  Балансировка `--balance` к режиму `lpt` не применяется: он балансирует
  загрузку сам, по построению. `Assignment.target_load` в нём возвращается как
  СПРАВОЧНАЯ идеальная загрузка `sum s(c_i) / m` (нижняя оценка makespan), а не
  как порог насыщения.

  *Балансировка* (`--balance`, по умолчанию `load`) не даёт одной паре забрать
  почти все грузы -- иначе раунды Шага 4 вырождаются в "одна пара везёт,
  остальные простаивают". Правило LPT-подобное, **по стоимости**: считается
  целевая загрузка `target = (сумма стоимостей всех грузов) / (число пар)`, где
  стоимость каждого груза берётся у той пары, которую правило режима для него и
  выберет; пара с накопленной загрузкой `>= target` дальше грузы не получает, и
  груз уходит следующей допустимой паре. Остаток (все пары насыщены) достаётся
  паре с минимальной накопленной загрузкой. `--balance none` отключает
  ограничение полностью -- строго по тексту алгоритма.

- **Шаг 4. Выполнение доставки** (`scheduler.py`, `RUN-STATIC`). Все
  назначенные доставки выполняются параллельно, по раундам: в раунде `r`
  каждая пара везёт `r`-й груз из своего списка (сперва все доставили первый
  груз, затем второй, и так далее). Внутри раунда для каждой пары:
  1. `ESTIMATE-TASK-COST` от ФАКТИЧЕСКИХ позиций её роботов и с накопленным
     глобальным `built`. Маршруты -- минимальные в графе; непостроенная
     переправа "стоит" при выборе маршрута свою длину, т.е. каждый мост жадно
     выбирается минимальной длины. Строитель строит только необходимые для
     этой доставки мосты (доезд доставщика до погрузки и до разгрузки) плюс
     те, что нужны ему самому, чтобы добраться до этих мостов; встречаться
     роботам не требуется.
  2. Если один и тот же ещё не построенный мост нужен нескольким парам этого
     раунда -- его строит **случайно выбранная** пара, для остальных проезд
     бесплатен (и остаётся бесплатным во всех последующих раундах, т.к. `built`
     глобален). Воспроизводимость -- через `rng_seed`.
  3. Барьер: длительность раунда -- по самой долгой доставке, разница идёт в
     `idle_total`.
  4. Позиции: доставщик -- в точке разгрузки, строитель -- в конце последнего
     ЛИЧНО построенного им моста (если сам ничего не строил -- на месте).

- **Шаг 5. Остановка.** Когда у всех пар закончились грузы, записывается общая
  стоимость выполнения всех операций `real = W_d_total + W_b_total`. Результат
  прогона -- план доставок (`RunResult.T`, по записи на доставку) плюс
  эвристическая оценка стоимости.

## Установка

```bash
python -m venv venv
venv\Scripts\activate          # Linux/macOS: source venv/bin/activate
pip install -r requirements.txt
```

Нужен Python ≥ 3.9. Единственная внешняя зависимость -- `matplotlib` (для
графиков); граф, Дейкстра и планировщик реализованы на чистом Python.

## Список эвристик приоритета груза

```bash
python -m robot_delivery_static.cli --list-heuristics
```

| Ключ | Формула | Смысл |
|---|---|---|
| `direct` | p = W_T | Дороже доставка данной парой -- выше приоритет (эвристика постановки) |
| `inverse` | p = 1 / W_T | Дешевле доставка -- выше приоритет |
| `random` | p ~ U(0,1) | Baseline: не зависит от стоимости вообще |

## Прогон экспериментов

```bash
python -m robot_delivery_static.cli \
    --heuristics direct inverse random \
    --assignment literal cheapest lpt \
    --n-islands 20 \
    --n-pairs 3 \
    -n 20 \
    --n-runs 10 \
    --seed 42 \
    --trace \
    --output-dir outputs
```

Число грузов пробегает диапазон от `--n-pairs` до `-n` включительно; на каждое
значение генерируется `--n-runs` независимых случайных сценариев, и все
комбинации "эвристика x режим назначения" прогоняются на ОДНИХ И ТЕХ ЖЕ
инстансах. В `--output-dir` сохраняются:

- `experiment_results.csv` -- сырые данные по каждому прогону (вариант,
  эвристика, режим назначения, балансировка, параметры LPT, seed, размеры
  сценария, `real`, `estimated_static`, `estimated_raw`, `gap_static`,
  `gap_raw`, `idle_total`, число раундов, `max_pair_load`, `max_pair_cost`,
  `cost_imbalance`, флаги достижимости и полной доставки);
- `real_vs_estimated_bars.png` -- средние `real` / `estimated_static` /
  `estimated_raw` по каждому варианту;
- `gap_static_vs_ncargos.png` -- насколько статическая оценка Шага 3 расходится
  с фактом в зависимости от числа грузов (главный график этой модели);
- `gap_raw_vs_ncargos.png` -- то же для контрольной оценки;
- `pair_load_balance.png` -- сколько грузов достаётся самой загруженной паре
  (пунктир -- идеально равномерное `n_cargos / n_pairs`);
- `pair_cost_balance.png` -- перекос загрузки пар по СТОИМОСТИ:
  `cost_imbalance = max_pair_cost / (real / n_pairs)`, где `max_pair_cost` --
  фактическая работа самой загруженной пары. `1.0` -- идеальный баланс; это и
  есть величина, которую минимизирует LPT (одинаковое ЧИСЛО грузов у пар ещё
  не значит одинаковую работу);
- `real_vs_ncargos.png` и `win_rate.png` -- при более чем одном варианте;
- `round_trace.png` -- при `--trace`: накопительные real/оценки по раундам
  одного прогона.

### Сравнение эвристик приоритета

```bash
python experiments/compare_priority_heuristics.py --n-islands 18 --n-pairs 3 -n 24 --n-runs 15 --seed 0
```

Результат на этих параметрах (330 полностью доставленных прогонов на
эвристику, режим назначения `literal`, балансировка `load`):

| Эвристика | средний `real` | средний `gap_static` |
|---|---|---|
| `direct` (постановка) | 4026.7 | +77.1% |
| `inverse` | **3494.9** | **+37.5%** |
| `random` (baseline) | 3824.9 | +57.2% |

То есть при буквальном правиле назначения прямая эвристика оказывается хуже
случайного baseline, а обратная -- лучше обеих. Причина видна из самого
правила: при `p = W_T` первая же запись свёрнутого списка отдаёт груз паре, для
которой он самый дорогой, и так для каждого груза (см. следующий эксперимент).

### Сравнение режимов назначения (буквальное правило vs greedy-nearest)

```bash
python experiments/compare_assignment_modes.py --heuristics direct inverse --n-islands 18 --n-pairs 3 -n 24 --n-runs 15 --seed 0
```

Результат на этих параметрах (по 330 прогонов на вариант, все сценарии
доставлены полностью):

| Вариант | средний `real` | `gap_static` | win-rate |
|---|---|---|---|
| `direct/literal` | 4026.7 | +77.1% | 7.3% |
| `direct/cheapest` | 3752.9 | +40.9% | 21.2% |
| `inverse/cheapest` | 3505.1 | +37.6% | 58.2% |
| `inverse/literal` | **3494.9** | +37.5% | **58.8%** |

Два вывода, которые этот эксперимент и должен был проверить:

1. **Буквальное правило "груз -- паре из записи с наивысшим приоритетом"
   болезненно именно для прямой эвристики**: `direct/literal` дороже
   `direct/cheapest` на 7.3%. Для обратной эвристики буквальное правило и
   greedy-nearest практически совпадают (`inverse/literal` ≈ `inverse/cheapest`,
   разница 0.3%) -- это ожидаемо, ведь `1/W_T` максимален там же, где `W_T`
   минимален, т.е. буквальный проход по списку при `inverse` сам по себе
   отдаёт груз самой дешёвой паре.
2. **Завышение статической оценки растёт с числом грузов** (`gap_static`,
   усреднение по 15 прогонам на точку):

   | Вариант | n=3 | n=6 | n=12 | n=18 | n=24 |
   |---|---|---|---|---|---|
   | `direct/literal` | +14.4% | +58.0% | +67.6% | +95.8% | +120.2% |
   | `direct/cheapest` | +7.2% | +25.5% | +42.8% | +47.6% | +68.7% |
   | `inverse/literal` | +4.3% | +26.0% | +42.8% | +40.0% | +70.8% |
   | `inverse/cheapest` | +4.3% | +28.1% | +40.1% | +39.4% | +69.5% |

   Это прямое измерение того, о чём говорит постановка: чем длиннее очередь
   грузов у пары, тем сильнее оценка "от начальной позиции при пустом `built`"
   расходится с фактическим исполнением, где роботы уже сместились, а часть
   переправ уже построена.

### Сравнение LPT с остальными режимами назначения

```bash
python experiments/compare_lpt_assignment.py --n-islands 18 --n-pairs 3 -n 24 --n-runs 15 --seed 0
```

Результат на этих параметрах (по 330 полностью доставленных прогонов на
вариант, эвристика `direct`; `перекос` -- `cost_imbalance`, идеал 1.000):

| Вариант | средний `real` | `gap_static` | перекос | `idle_total` |
|---|---|---|---|---|
| `direct/literal` | 4026.7 | +77.1% | 1.368 | 1580.1 |
| `direct/cheapest` | **3752.9** | +40.9% | 1.303 | 1210.4 |
| `direct/lpt-completion` | 3803.0 | **+38.3%** | 1.249 | 1186.8 |
| `direct/lpt-load` | 3820.7 | +54.3% | **1.217** | **1182.8** |

Главный вывод: **LPT выигрывает ровно там, где и должен -- по балансу, а не по
сумме**. Оба его варианта дают минимальный перекос загрузки пар и минимальный
простой на барьерах раундов, обходя по этим метрикам и буквальное правило, и
greedy-nearest; по суммарной стоимости `real` LPT уступает greedy-nearest 1.3%.
Это ожидаемо и является содержательным результатом эксперимента: LPT --
эвристика для МАКСИМУМА (`P||C_max`), а `real` -- сумма. Если бы стоимость
груза не зависела от позиции пары, сумма вообще не зависела бы от
распределения; вся её зависимость от `π` возникает из перемещений роботов между
доставками и общих мостов и с балансировкой максимума никак не связана.
Поправка `completion` на неидентичность пар отыгрывает у чистого Грэма и часть
суммы, и точность статической оценки (`gap_static` +38.3% -- лучший результат
среди всех режимов вообще), уступая ему только по самому балансу.

Роль порядка (этап B) проверяется прогоном тех же трёх эвристик в режиме `lpt`:

```bash
python experiments/compare_lpt_assignment.py --heuristics direct inverse random --assignment lpt
```

| Порядок разбора | средний `real` | перекос | `idle_total` |
|---|---|---|---|
| `direct` = LPT (длинные первыми) | 3820.7 / 3803.0 | **1.217** / 1.249 | **1182.8** / 1186.8 |
| `inverse` = SPT (короткие первыми) | **3718.8** / **3585.2** | 1.319 / 1.330 | 1653.3 / 1588.2 |
| `random` = list scheduling | 3806.9 / 3731.9 | 1.275 / 1.297 | 1630.9 / 1542.5 |

(через `/`: правило `load` / правило `completion`.) Порядок "длинные работы
первыми" действительно даёт лучший баланс и наименьший простой -- то, ради чего
LPT и придуман, -- а обратный порядок (SPT) даёт меньшую сумму ценой заметно
худшего баланса и на 40% большего простоя.

## Программное использование

```python
from robot_delivery_static.scenario import generate_scenario
from robot_delivery_static.experiment import run_single

scenario = generate_scenario(n_islands=18, n_cargos=12, n_pairs=3, seed=1)
result, bracket = run_single(scenario, "direct", assignment_mode="literal", balance="load")

print(result.feasible, result.all_delivered, result.n_rounds)
print(result.plan)          # {pair_id: [cargo_id, ...]} -- распределение Шага 3
print(bracket.real, bracket.estimated_static, bracket.gap_static)
```

Или по шагам, если нужен доступ к промежуточным структурам:

```python
from robot_delivery_static.assignment import assign_cargos, build_cost_table
from robot_delivery_static.pairing import form_pairs
from robot_delivery_static.priority import get_cargo_heuristic
from robot_delivery_static.scheduler import run_static

pairing = form_pairs(scenario.G, scenario.deliverer_positions, scenario.builder_positions)
table = build_cost_table(scenario.G, pairing.pairs, scenario.cargos)          # Шаг 3, этап 1
assignment = assign_cargos(table, pairing.pairs, scenario.cargos,             # Шаг 3, этап 2
                           get_cargo_heuristic("direct"), mode="literal")
result = run_static(scenario.G, scenario.cargos, scenario.deliverer_positions,
                    scenario.builder_positions, get_cargo_heuristic("direct"))
```

Распределение по LPT -- отдельной точкой входа (эквивалентно
`assign_cargos(..., mode="lpt")`, но параметры алгоритма видны явно):

```python
from robot_delivery_static.assignment import assign_lpt

lpt = assign_lpt(table, pairing.pairs, scenario.cargos,
                 get_cargo_heuristic("direct"),   # порядок: direct = LPT, inverse = SPT
                 size_rule="min",                 # размер задачи: min / mean / max
                 rule="completion")               # выбор пары: load / completion
print(lpt.per_pair)      # {pair_id: [cargo_id, ...]} -- очереди пар
print(lpt.target_load)   # справочная идеальная загрузка (нижняя оценка makespan)

result = run_static(scenario.G, scenario.cargos, scenario.deliverer_positions,
                    scenario.builder_positions, get_cargo_heuristic("direct"),
                    assignment_mode="lpt", lpt_size="min", lpt_rule="completion")
```

## Принятые решения и допущения реализации

- **Паросочетание Шага 2 -- жадное**, по возрастанию расстояний, а не
  оптимальное по сумме (венгерское): это буквальное прочтение "по принципу
  минимального расстояния".
- **Расстояние доставщик-строитель** считается по графу с учётом всех
  переправ, доступных к возведению, но БЕЗ учёта стоимости их постройки -- так
  же, как критерий выбора доставщика в `dynamic_v2`.
- **Два режима назначения** (`literal` / `cheapest`) -- обе трактовки фразы
  "жадно присваивая каждой паре наиболее приоритетный груз"; по умолчанию
  `literal` (буквально по тексту алгоритма). Третий режим (`lpt`) -- уже не
  трактовка постановки, а внешняя эвристика теории расписаний, добавленная для
  сравнения.
- **LPT реализован как полноценный алгоритм**, а не как порог загрузки:
  собственный порядок разбора (по убыванию размера задачи) + собственное
  правило выбора пары. Ранее существовавшая балансировка `--balance load` --
  это лишь LPT-ПОДОБНОЕ ограничение сверху для режимов `literal`/`cheapest`,
  она не меняет ни порядок разбора, ни правило выбора пары.
- **Размер задачи в LPT приходится сворачивать** (`--lpt-size`), потому что
  пары роботов -- НЕидентичные машины: стоимость одного и того же груза у
  разных пар разная, и единого "времени обработки", которое требует
  классический LPT, у задачи просто нет. По умолчанию берётся `min` -- оценка
  у лучшего исполнителя, чтобы груз не получал завышенный размер из-за
  какой-нибудь заведомо далёкой пары.
- **Балансировка `load`** (по умолчанию) не описана в постановке явно, но без
  неё одна пара может забрать почти все грузы, и параллельная схема раундов
  Шага 4 вырождается. Порог считается по стоимости той пары, которую правило
  режима реально выберет -- иначе при обратной эвристике порог оказывается
  многократно выше назначаемых стоимостей и балансировка не срабатывает вовсе.
  Полностью выровнять ЧИСЛО грузов такое правило не обязано (оно выравнивает
  суммарную работу): на дефолтных параметрах самой загруженной паре достаётся
  ~10-12 грузов из 24 при равномерных 8. Отключается `--balance none`.
- **Порядок грузов внутри списка пары** -- порядок назначения, т.е. по
  убыванию приоритета; исключение -- грузы, попавшие в остаток (все пары были
  насыщены), они дописываются в конец списка.
- **`estimated_static` не обязана быть больше `real`.** Начальная позиция пары
  может оказаться и ближе к очередному грузу, чем фактическая позиция того
  момента, когда пара за него берётся, поэтому отрицательный `gap_static` на
  отдельных сценариях -- не ошибка, а измеряемое свойство. Гарантированное
  неравенство `estimated_raw >= real` проверяется тестом
  `test_estimated_raw_never_below_real`.
- **Груз, недостижимый для всех пар**, остаётся в `RunResult.undelivered`, и
  прогон завершается с `all_delivered = False` (перераспределить его в
  статической модели некому). Шаг 0 такие сценарии в норме отсекает заранее.
- Возведённые переправы -- глобальное состояние для всех пар и раундов:
  однажды построенный мост никогда не строится повторно (тест
  `test_bridges_never_rebuilt_across_rounds`).
